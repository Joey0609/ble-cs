Shared DRBG state across steps and procedures

  1. Before each procedureUpdate the key/nonce state for backtracking resistance before generating that procedure’s random bits.
  2. For each transactionAES-128 generates bit blocks using the step counter, transaction ID and transaction counter.
  3. At both peersConsume bits in the specified step, role and transaction order; retain unused bits for that transaction type.
shared state + identical invocation rules → matching channels, packets and tone choices
A subevent boundary does not reseed the DRBG. A new procedure evolves its state; a CS Security Start exchange reinitializes it.
Core 6.0 · Vol 6, Part E, §3·Vol 6, Part H, §4.8

The CS_DRBG uses the AES-128 security function e. h9 derives the initial key and nonce vector; f9 participates in their updates. Backtracking resistance is invoked whenever CSProcCount is incremented, before the first CS_DRBG invocation for that procedure. It is intended to protect earlier outputs if the current state becomes known. The step counter continues through a procedure’s subevents; transaction IDs separate the different uses. Counters and bit-consumption rules keep both controllers synchronized without transmitting every random choice. This is controller behavior; the planner’s example pseudo-random channel sequence does not reproduce the secure on-air sequence.
