Practical implementation: four decisions

A CS configuration that works on paper still has to fit the link, the controllers and the application.

  1. Step budgetMode-0 steps, subevents, spacing and the controllers' step timings add up to one time budget. More measurements mean more radio time and more energy.
  2. Result message sizeThe Attribute Protocol maximum transmission unit (ATT MTU) makes a procedure's result take 39 notifications by default or 2 at 498.
  3. ACL intervalSets what fits in the schedule: CS events and RAS results share its events, so the interval decides how a procedure is split and how often it can run.
  4. SecuritySet by the use case: the required CS security level follows from what a wrong distance would cost.
Build the time budget from the step up, then check it against the use case.

This stack turns the previous sections into four decisions an implementer has to make, and builds them from the smallest unit up. First, the step budget: the step timings both controllers support, mode-0 steps, subevents and their spacing all spend the same time, and every added measurement is radio time, which is energy. Second, the ATT MTU, exchanged once after the connection is set up: it decides how many notifications, and so how much ACL airtime, the reflector's RAS results need. Third, the ACL connection interval: CS events are anchored to ACL events, and on our controller each must end within one interval, so once the procedure and its results are known, the interval decides how the procedure is split into CS events and how often procedures can repeat. Fourth, security: the CS security level is chosen per use case, because each use case loses something different when a distance is wrong.
