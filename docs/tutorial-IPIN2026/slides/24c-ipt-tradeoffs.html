IPT capability, timing and data tradeoffs

Implementation choiceConsequence
Negotiate and enable IPTCheck the reflector capability and accepted configuration; IPT is disabled by default.
Allow phase-transfer timingBudget antenna switching and the interlude: the reflector must measure, compute and settle the transmit phase.
Drop RAS entirelyPhase-slope PBR from the initiator alone, with no result traffic to schedule; no RTT, reflector amplitude or quality. The app’s Reflector data: None requires IPT.
Keep RAS with IPTSame PCT field size, amplitude only (Q = 0): RAS still returns quality and RTT, but the reflector phase is gone for diagnostics.
Less result traffic frees ACL airtime; longer IPT tone timing can spend it again.
Core 6.3 · Vol 6, Part B, CS capabilities/configuration·Vol 6, Part H, §4.3·Vol 6, Part A, §6.5

The prerequisite is Channel Sounding Enhancement #1 with support for IPT in the CS reflector. Use the IPT feature/configuration path and verify the returned state, rather than enabling it because of a version label. The reflector declares separate antenna-switch and interlude timing support for IPT. Its RF chain must accurately apply and settle the phase for the appropriate antenna path. The standard PCT report remains an I/Q field with Q = 0; bandwidth savings are realized only if the host/reporting route avoids transferring data it no longer needs. IPT does not supply the reflector timing measurement needed for paired RTT. Losing the separately reported reflector phase reduces offline diagnostic options: an error in the applied phase arrives as channel phase, and so as distance. Keep a non-IPT mode, or mode-3 RTT as a cross-check, for commissioning and fault diagnosis. In this project, Reflector data None is accepted only for an initiator configuration with IPT requested; the initiator then skips RAS discovery and subscription, and the app shows RTT as unavailable. Hardware support and measured end-to-end performance must be checked for the selected board/controller.
