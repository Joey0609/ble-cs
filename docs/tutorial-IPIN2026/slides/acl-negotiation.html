ACL timing and MTU negotiation

An ACL link has timing parameters; Link Layer data length and ATT MTU are negotiated separately

Optional connection parameter update

Link Layer · Central-initiated example

Central→ LL_CONNECTION_PARAM_REQinterval range, latency, timeout
Peripheral→ LL_CONNECTION_PARAM_RSP
Central→ LL_CONNECTION_UPDATE_INDnew timing starts at the indicated event

The connection stays up. A parameter update is optional; either side can request one when supported.

Link Layer data length

Maximum data in one LE data PDU

Controller→ LL_LENGTH_REQmaximum Tx/Rx octets and times
Controller→ LL_LENGTH_RSPpeer's maximum Tx/Rx octets and times

This project configures up to 251 octets per PDU; the peer/controller may support less.

ATT MTU

GATT · Client starts the exchange

ATT Client→ ATT_EXCHANGE_MTU_REQClient receive MTU
ATT Server→ ATT_EXCHANGE_MTU_RSPServer receive MTU

Effective MTU = the smaller receive limit. This project allows up to 498 octets; a peer can lower it.

Two different limits: LL data length caps one radio PDU; ATT MTU caps one ATT PDU. A larger ATT PDU can span several LL data PDUs.

ATT Client/Server roles are separate from Central/Peripheral; in the RAS route, the Initiator is Client and the Reflector is Server.

Initial timing is carried in the CONNECT_IND or AUX_CONNECT_REQ described on the previous slide. A later update is optional. This card illustrates one common Central-initiated Link Layer Connection Parameters Request procedure: Central sends LL_CONNECTION_PARAM_REQ, Peripheral responds with LL_CONNECTION_PARAM_RSP, and Central sends LL_CONNECTION_UPDATE_IND. The new parameters take effect at the indicated connection event. Either side may initiate a request when the procedure is supported; fallback/update paths differ with peer capability. LL_LENGTH_REQ and LL_LENGTH_RSP exchange each controller's maximum transmit and receive octets and times. The effective transmit size depends on both devices' capabilities. This project configures up to 251 octets per LE data PDU. ATT Exchange MTU is an ATT procedure over GATT. ATT_EXCHANGE_MTU_REQ carries the Client's receive MTU; ATT_EXCHANGE_MTU_RSP carries the Server's receive MTU. Both sides use the smaller receive value. This project configures an ATT MTU limit of 498 octets and enables automatic exchange; the peer may yield a lower negotiated result. An ATT PDU is carried within L2CAP, which may segment it across multiple Link Layer data PDUs. In the project RAS path, notifications carry reflector step data, so a larger effective ATT MTU can reduce fragmentation. Sources: Bluetooth Core Specification 6.2, Vol 6 Part B, Sections 5.1.1 (Connection Update), 5.1.7 (Connection Parameters Request) and 5.1.9 (Data Length Update); Vol 3 Part F, Section 3.4.2 (ATT MTU exchange); repository configuration in cs_client/prj.conf and cs_hostless_initiator/prj.conf.
