Message size sets how long RAS holds the link

The Attribute Protocol maximum transmission unit (ATT MTU) sets notification size; Link Layer protocol data units (PDUs) carry them

Two limits decide how many ACL packets a ranging result needs, and both are negotiated on the new link, as the connection-establishment slide listed. The Link Layer data length sets the payload of one LL data PDU: 27 octets by default, up to 251 with the Data Length Update procedure (LL_LENGTH_REQ/RSP), which either controller may start at any time; this project allows 251. The ATT MTU sets the largest notification: 23 octets by default. The ATT client sends ATT_EXCHANGE_MTU_REQ only once per connection, and both sides then use the smaller receive MTU for the rest of the connection. This project offers 498 and starts the exchange automatically on connection; if the peer offers less, or the exchange never happens, every procedure's results need more notifications. ATT client and server are separate from Central and Peripheral: in the RAS route the initiator is the client and the reflector the server. The layers nest. A RAS real-time notification is an ATT notification (3 octets: opcode and handle) whose value starts with a 1-octet RAS segment header. The ATT PDU travels in an L2CAP basic frame with a 4-octet header, and L2CAP segments that frame across as many LL PDUs as needed. With defaults, 23 − 3 − 1 = 19 octets of results fit in one notification. With MTU 498, 498 − 3 − 1 = 494 octets fit, and 498 + 4 = 502 = 2 × 251, so a full notification fills exactly two full LL PDUs. Sizing uses the baseline workload of the previous slides: 72 channels once in mode 2, two mode-0 steps, one antenna path. The reflector's RAS record is a 4-octet ranging header, an 8-octet subevent header 10 octets per mode-2 step (step mode, antenna permutation index, and a phase and quality entry for the path and the extension slot) and 4 per mode-0 step, 740 octets in all. That is 39 notifications at MTU 23 and 2 at MTU 498. The planner charges each LL PDU with the Central's empty poll and two T_IFS gaps: 26 ms of ACL airtime at MTU 23 on LE 1M against 8 ms at 498; on LE 2M, 19 ms against 4.6 ms. The planner leaves out the 4-octet MIC of the encrypted link, under 2 percent. The airtime turns into schedule, which the next slide draws. RAS results travel in ACL events that carry no CS event, so at a 15 ms interval the default MTU needs two such events per procedure and 498 needs one: a procedure every 3 intervals (22 per second) or every 2 (33 per second). At 7.5 ms the default MTU needs four events. Leave margin above that floor: in our lab runs one ACL event between procedures lost the RAS data of 0.5 to 1.5 percent of procedures, more for larger payloads, which is why the hostless initiator's default repeats procedures every 3 intervals. If the configuration selects no reflector data, which requires IPT, none of this traffic exists.
